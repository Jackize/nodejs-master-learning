Kafka zero — topic & consumer group

Win: tạo topic shopstream.order.paid (3 partitions); produce / consume bằng CLI; giải thích được consumer group + offset — chưa nối Nest.

⏱ ~60–90 phút · 🎯 Hands-on Docker Kafka đã có từ Bài 00 · verify apache/kafka:4.3.1 · docs: Kafka Quickstart.

✍️ Tự làm

Không pre-fill Nest. Bài này chỉ CLI trong container Kafka. Đóng góp vào ShopStream: topic thật shopstream.order.paid sẵn cho producer Nest (bài sau). Cheat-sheet Module 2 vẫn dùng khi ôn order flow.

🌉 Bắc cầu

Bài 14 T1: sau paid cần notify tin cậy → Kafka. Trước khi ClientKafka trong Nest, bạn phải sờ topic / partition / consumer group — nếu không, Nest chỉ là wrapper mơ hồ. Broker đã chạy từ Bài 00.

💡 Topic · Partition · Consumer group (1 phút)

Topic = tên log append-only (vd event “order đã paid”).
Partition = “làn” song song trong topic — scale consume; cùng key → cùng partition (thứ tự theo key).
Consumer group = nhiều process cùng group.id chia partitions; mỗi partition chỉ 1 member trong group xử lý → scale ngang, không nhân đôi mọi message cho mọi member.

0. Chuẩn bị

bash — shopstream/ 
cd shopstream
docker compose up -d kafka
docker compose ps
# kafka phải Up (healthy)

Mọi lệnh dưới chạy từ thư mục shopstream/. Trong container, bootstrap = localhost:9092.

1. Tạo topic ShopStream (đóng góp dự án)

bash — tạo shopstream.order.paid 
docker compose exec kafka /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server localhost:9092 \
  --create \
  --topic shopstream.order.paid \
  --partitions 3 \
  --replication-factor 1 \
  --if-not-exists

docker compose exec kafka /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server localhost:9092 \
  --describe \
  --topic shopstream.order.paid

Bạn phải thấy PartitionCount: 3. Local RF=1 (1 broker). Production RF≥3 — phỏng vấn hay hỏi.

Cảnh báo dấu chấm trong tên topic

Kafka warn: đừng trộn . và _ lung tung (metric name). ShopStream thống nhất shopstream.<domain>.<event> — ổn nếu nhất quán.

2. Produce (ghi event)

Cách A — vài dòng nhanh (không key; thường dồn 1 partition):

bash — produce không key 
printf '%s\n' 'order-1 paid' 'order-2 paid' 'order-3 paid' | \
docker compose exec -T kafka /opt/kafka/bin/kafka-console-producer.sh \
  --bootstrap-server localhost:9092 \
  --topic shopstream.order.paid

Cách B — có key (nên làm): cùng userId/orderId → cùng partition → giữ thứ tự theo entity:

bash — produce có key (Kafka 4.3: --reader-property) 
printf '%s\n' \
  'ord-1:{"orderId":"ord-1","status":"paid"}' \
  'ord-2:{"orderId":"ord-2","status":"paid"}' \
  'ord-3:{"orderId":"ord-3","status":"paid"}' \
  'ord-1:{"orderId":"ord-1","status":"paid"}' | \
docker compose exec -T kafka /opt/kafka/bin/kafka-console-producer.sh \
  --bootstrap-server localhost:9092 \
  --topic shopstream.order.paid \
  --reader-property parse.key=true \
  --reader-property key.separator=:

3. Consume + consumer group

bash — đọc từ đầu, gắn group 
docker compose exec kafka /opt/kafka/bin/kafka-console-consumer.sh \
  --bootstrap-server localhost:9092 \
  --topic shopstream.order.paid \
  --group shopstream-notify-v1 \
  --from-beginning \
  --formatter-property print.key=true \
  --formatter-property print.partition=true
# Ctrl+C khi đã thấy message

Chạy lại cùng --group shopstream-notify-v1 không --from-beginning: gần như không in lại — offset đã commit. Đó là “đã xử lý tới đâu” của group.

bash — xem offset / lag 
docker compose exec kafka /opt/kafka/bin/kafka-consumer-groups.sh \
  --bootstrap-server localhost:9092 \
  --describe \
  --group shopstream-notify-v1

Cột CURRENT-OFFSET / LOG-END-OFFSET / LAG: lag=0 nghĩa là group đã đuổi kịp (khi không còn member active vẫn thấy offset đã lưu).

4. Thí nghiệm bắt buộc — 2 group ≠ 1 group

Tình huốngKỳ vọng
Hai consumer cùng --group shopstream-notify-v1Chia partitions; mỗi message chỉ 1 trong 2 nhận (trong group)
Consumer group khác shopstream-analytics-v1 + --from-beginningĐọc lại toàn bộ — group riêng = subscriber độc lập

Cách làm nhanh: mở 2 terminal, cùng topic, khác group id, cả hai --from-beginning — cả hai in cùng payload. Đổi thành cùng group → message không nhân đôi cho mọi member (chia theo partition).

Góc phỏng vấn

Q: Consumer group dùng để làm gì?
A: Scale consume ngang + đảm bảo mỗi partition chỉ một member trong group xử lý. Muốn mọi service nhận đủ event → group id khác nhau (notify vs analytics). Liên hệ Bài 12: idempotency HTTP; Kafka at-least-once → consumer vẫn có thể nhận trùng → cần idempotent handler (bài sau).

6. Câu hỏi tư duy

Khi Nest consumer xử lý order.paid rồi crash trước khi commit offset, message sẽ được giao lại (at-least-once). Liên hệ Bài 12 Idempotency-Key: handler notify phải idempotent thế nào (theo orderId)?
